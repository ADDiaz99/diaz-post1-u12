# ADR-001: Capas simples para la persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado

Aceptado. Fecha: 2026-11-04.
                 (YYYY-MM-DD)
## Contexto

Tras integrar Chain of Responsibility (validación), Strategy (cálculo por categoría) y Observer
(notificación) en el sistema de solicitudes de reembolso, hay que decidir si el proyecto migra a
una arquitectura Hexagonal completa, con puertos e interfaces intermedias para todas sus
dependencias externas, o si se mantiene en capas simples.

La Guía de la unidad (sección 6.2) da el criterio: Hexagonal vale la pena en sistemas que vivirán
3 años o más **con cambios de infraestructura**. El criterio se evalúa con datos de este proyecto y
por separado para cada dependencia externa:

- **Persistencia.** No existe ningún plan de cambiar de motor de base de datos. El servicio usa tres
  operaciones del repositorio: `save`, `findById` y el método derivado `findByEmpleadoIdAndEstado`.
  El dominio ya no depende de JPA: `SolicitudReembolso` no tiene anotaciones y su mapeo está en
  `src/main/resources/META-INF/orm.xml`.
- **Notificación.** Contabilidad anunció para el próximo trimestre una integración por API externa
  para pagar las solicitudes aprobadas. Hoy el servicio avisa a `List<ObservadorCambioEstado>` y no
  conoce a ningún notificador concreto.

## Opciones consideradas

1. **Hexagonal completa:** puerto `RepositorioSolicitudes` en `aplicacion`, adaptador JPA en
   `infraestructura` y, por simetría, un puerto de notificación con su adaptador.
2. **Puerto solo para la persistencia** y la notificación como está.
3. **Capas simples para la persistencia** y la notificación como está.

## Decisión

Se elige la **opción 3**.

**Persistencia:** `SolicitudReembolsoService` sigue dependiendo directamente de
`RepositorioSolicitudesJpa`, sin una interfaz de puerto intermedia. Hoy un puerto de persistencia
sería una abstracción especulativa (YAGNI): tendría una sola implementación posible y ningún caso de
uso que pida otra. Agregaría al menos una interfaz y un adaptador que solo reenvía llamadas. El
beneficio que sí interesa, que el dominio se pruebe y evolucione sin la base de datos, ya se obtiene
porque el dominio no importa JPA.

**Notificación:** no se introduce ningún cambio. `ObservadorCambioEstado` ya es el seam necesario:
el próximo trimestre `NotificadorContabilidad` podrá reemplazar su implementación interna por una
llamada a la API externa (o se agregará un observador nuevo) sin modificar
`SolicitudReembolsoService` ni los demás observadores. Un puerto adicional encima de esa interfaz
sería una segunda abstracción para el mismo punto de variación.

Las reglas de `ReglasArquitectura` son coherentes con esta decisión: verifican los límites que sí
existen (procesamiento sin persistencia ni web, controlador que solo usa el servicio, dominio sin
frameworks) y ninguna supone puertos de persistencia.

## Consecuencias

**Positivas**

- No se agregan interfaces ni mappers de persistencia sin un caso de uso real que los justifique.
- El único cambio de infraestructura con fecha conocida (la integración de Contabilidad) ya tiene su
  punto de extensión listo y probado.
- Hay menos indirección: quien lee el servicio ve directamente qué repositorio usa.

**Negativas**

- Si en el futuro se cambia de motor de base de datos o se necesita otra fuente de datos, el puerto
  de persistencia tendrá que introducirse después. Se acepta esa deuda técnica de forma consciente;
  el costo es acotado porque solo `SolicitudReembolsoService` usa el repositorio.
- Un revisor que espere simetría total (puertos en todas las dependencias externas) puede leer la
  asimetría como una inconsistencia si no conoce este ADR.
- El servicio de aplicación no se puede probar sin un repositorio de Spring Data (o un doble de
  prueba de esa interfaz). Hoy se cubre con la prueba de integración sobre H2.

## Señales para revisar esta decisión

- Un plan concreto de cambiar de base de datos, o de leer solicitudes desde otro sistema.
- La necesidad de probar la lógica del servicio sin Spring de forma frecuente (por ejemplo, si
  crece tanto que la prueba de integración deja de ser suficiente).
- Para la notificación: que la integración de Contabilidad exija reintentos, colas o
  procesamiento asíncrono. Eso podría justificar un mecanismo de eventos, pero no antes.
